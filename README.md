# 가게 이익 노트 (베타)

음식점 운영자가 홀·배달·포장 매출과 비용을 기록하고, 실적 변화의 원인을 확인하고, 해결안을 실행한 뒤 **가게 전체 영업이익**이 나아졌는지 확인하는 웹앱입니다. 매출 증가만으로 성공을 판단하지 않고, 비용을 반영한 영업이익을 함께 봅니다.

백엔드·로그인·유료 API 없이 브라우저만으로 동작합니다.

## 실행 방법

Node.js 18 이상이 필요합니다. (개발 환경: Node 24, npm 11)

```bash
npm install        # 의존성 설치
npm run dev        # 개발 서버 실행 → 터미널에 표시되는 주소(기본 http://localhost:5173) 접속
npm test           # 계산 단위 테스트 + 화면 스모크 테스트
npm run build      # 타입 검사 후 프로덕션 빌드 (dist/)
npm run preview    # 빌드 결과 미리보기
```

### 배포 (GitHub Pages)

`main` 브랜치에 푸시하면 GitHub Actions(`.github/workflows/deploy.yml`)가 `npm ci` → `npm test` → `npm run build`를 차례로 실행하고, 모두 성공하면 `dist`를 GitHub Pages에 배포합니다. 저장소 설정의 Pages 소스는 **GitHub Actions**여야 합니다.

- 배포 경로(`BASE_PATH`, 예: `/store-profit-note/`)와 전체 주소(`SITE_URL`)는 워크플로가 Pages 설정에서 받아 빌드에 넘깁니다. 로컬 빌드는 `/` 기준입니다.
- 링크 공유 썸네일(`public/og-image.png`, 1200×630)은 `SITE_URL` 기준 전체 주소로 들어갑니다. 공유 미리보기는 서비스마다 캐시하므로 이미지를 바꾼 뒤에는 각 서비스의 공유 디버거(카카오 ‘공유 디버거’, Facebook Sharing Debugger)에서 캐시를 지우세요.
- 테스트는 날짜·시간대와 무관하게 같은 결과가 나오도록 ‘오늘’을 고정해 실행합니다(`src/test-setup.ts`, 시간대 Asia/Seoul).

### 홈 화면 앱(PWA)과 오프라인

- 웹 앱 매니페스트와 서비스 워커는 `vite-plugin-pwa`가 빌드 때 만듭니다. 아이콘: `public/icons/`(안드로이드 192·512px, 마스크형 512px, 아이폰 홈 화면 180px).
- 온라인에서 한 번 열면 앱 파일을 기기에 받아 두므로, 이후에는 오프라인에서도 앱을 열고 매출을 입력·저장할 수 있습니다(데이터는 기존처럼 이 기기의 localStorage에 저장).
- 새 버전은 앱을 완전히 닫았다가 다시 열 때 적용됩니다(입력 중에 화면이 저절로 새로고침되지 않도록).
- 데이터는 주소(출처)별로 따로 저장됩니다. 로컬 개발 주소(localhost)에서 입력한 데이터는 배포 주소에 보이지 않으므로 **가게 설정 → 데이터 관리**에서 백업 파일로 옮기세요. 또한 `https://<계정>.github.io` 아래의 모든 사이트는 같은 저장 공간을 쓰므로, 같은 계정에 다른 Pages 사이트를 올릴 때는 신뢰할 수 있는 것만 올리세요.

처음 접속하면 **샘플 데이터로 둘러보기** 또는 **내 가게 등록하기**를 고릅니다.

- 샘플: 가상의 식당·플랫폼·요율로 연속된 두 개의 28일 기간을 만듭니다(어제 기준). 홀 매출 감소, 배달 주문 증가와 주문당 이익 악화, 포장 증가가 함께 나타납니다. 샘플 사용 중에는 상단에 표시가 계속 보입니다. 모든 합계와 진단 결과는 화면에서 데이터로 계산하며 미리 적어 둔 값이 아닙니다.
- 내 가게: 가게명과 운영 채널만 입력하면 시작할 수 있습니다.

## 계산 기준

### 매출

- 순매출 = 할인·환불 반영 전 상품 판매액 − 가게 부담 할인액 − 환불액
- 완료 주문 수 = 전액 취소된 주문을 뺀 건수. 부분 환불은 환불액으로 입력
- 홀 객단가 = 홀 순매출 ÷ 홀 방문 고객 수
- 배달·포장 평균 주문금액 = 채널 순매출 ÷ 완료 주문 수
- 총매출 = 홀 + 배달 + 포장 순매출

### 비용과 영업이익

- 채널별 직접 비용 차감액 = 채널 순매출 − 채널 직접 비용
  (직접 비용에는 채널 전용 고정비도 포함될 수 있으므로 "기여이익"이라고 부르지 않습니다)
- 영업이익 = 채널별 직접 비용 차감액 합계 − 공통 운영비
- 영업이익률 = 영업이익 ÷ 총매출
- 직접 비용: 식재료비, 중개 수수료, 결제 수수료, 가게 부담 순배달비, 포장비, 홀 전용 소모품비, 채널 전용 광고비, 기타 직접 비용
- 공통 운영비: 인건비, 월세, 관리비, 공과금, 렌탈료, 보험료, 공통 광고비, 감가상각비, 기타 운영비
- 대출 이자와 원금 상환은 영업이익 계산에 넣지 않습니다(입력 항목 없음).

### 중복 방지 규칙

- **실제값 우선**: 한 비용 항목에 실제값이 있으면 추정값은 무시합니다. 두 값을 합산하지 않습니다.
- **귀속은 하나**: 기간 비용은 귀속(홀·배달·포장·공통) 하나만 가집니다. 채널이면 그 채널 직접 비용, 공통이면 공통 운영비로 한 번만 계산합니다. 같은 항목이 일별 입력과 기간 비용에 겹치면 경고합니다.
- **묶음 수수료**: 묶음 수수료를 쓰면 결제 수수료를 따로 부과하지 않습니다(입력도 차단).
- **순배달비**: 가게 지급 배달비 − 가게에 귀속되는 고객 부담 배달비로 입력하며, 고객 부담 배달비를 매출에 다시 더하지 않습니다.

### 기간 비용 안분

귀속 기간에 걸친 비용은 조회 기간과 겹치는 **달력 일수 비율**로 나눕니다.
예: 1월 월세 310만 원을 1월 1~10일로 조회하면 310만 × 10/31 = 100만 원.

### 추정과 비소급

- 수수료 추정은 주문 경로별 규칙(중개·결제 요율, 각각의 기준액, 건당 정액, 부가세 별도 여부, 적용 시작일)으로 계산합니다. 앱에는 실제 플랫폼 요율이 들어 있지 않습니다.
- 기준액은 상품 판매액 / 가게 부담 할인 차감 후 / 순매출 중에서 고릅니다(무조건 순매출로 가정하지 않음).
- 매출·주문 수를 입력하면 그 거래일·주문 경로에 적용되는 수수료 규칙, 주문 1건당 기본 비용(예: 포장비), 가게 설정의 식재료비 원가율을 자동으로 적용합니다. 빠른 입력에 보이는 금액은 저장할 때와 같은 계산(`fillEstimates`)이라 저장된 기록·대시보드 합계와 같습니다.
- 식재료비는 상품 판매액 × 원가율입니다. 가게 설정의 원가율(직접 지정, 판매 방식별 지정이 우선)이 있으면 그것을, 없으면 판매 중 메뉴의 단순 평균(판매량 미반영, 추정)을 씁니다. 기록 상세에서 직접 입력하거나 **임시 추정값 30%**를 고를 수도 있습니다. 30%는 업종 평균이나 검증된 기본값이 아닙니다.
- 추정값은 입력 시점에 그 날짜에 적용되는 규칙으로 계산해 실적에 **저장**합니다. 이후 수수료·가격·원가 설정을 바꿔도 이미 저장된 실적은 바뀌지 않습니다.

### 0, 미입력, 추정, 계산 불가

- 빈칸은 미입력(null)이고 0원과 다르게 다룹니다.
- 채널별 필수 비용 항목(예: 배달은 식재료비·중개/결제 수수료·순배달비·포장비)이 비어 있거나, 가게 설정의 공통비 체크리스트 항목이 조회 기간 전체를 덮지 않으면 영업이익을 **"데이터 필요"**로 표시하고 "입력된 값만 반영 시 ○○원(미확정)"을 참고로만 보여줍니다.
- 비용 금액은 근거에 따라 세 가지로 나눠 합산합니다 (`src/domain/costBasis.ts`).
  - **실제**: 영수증·정산서에서 확인해 입력한 금액. 있으면 항상 이 금액만 씁니다.
  - **설정 기준 계산**: 직접 정한 설정값(수수료율, 주문 1건당 금액, 직접 지정한 원가율)을 그 기록의 입력값(매출 금액·주문 수·카드 결제액)에 그대로 적용한 금액. 예: 주문 10건 × 건당 포장비 500원 = 5,000원.
  - **추정**: 계산에 필요한 값 하나라도 모르는 값을 가정한 금액. 예: 메뉴 원가율 단순 평균(판매 비중 미반영), 모르는 할인·환불 0원 가정, 임시 원가율 30%, 지난달 청구액을 가져온 기간 비용. 상세 화면에 무엇을 가정했는지 함께 보여줍니다.
- 데이터 판별과 화면 표시를 나눕니다. v7부터 자동 계산할 때 계산 내용(`calc`: 건당 금액·주문 수, 요율·기준금액, 원가율·기준 금액 등)을 함께 저장하고, 판별과 상세 표시는 이것을 씁니다. `calc`가 없는 이전 기록은 저장된 근거 문구(`estimateBasis`)로 판별하고 상세에도 그 문구를 그대로 보여줍니다. 근거 문구의 형식은 바꾸지 않습니다. 근거가 없거나 알아볼 수 없는 기존 값은 '추정 · 근거 불분명'으로 둡니다. 판매액 기준 이전 기록에서 할인·환불이 비어 있으면 그 금액이 반영되는 기준의 수수료도 추정으로 봅니다.
- 화면 표시: 설정대로 계산된 값과 실제 금액은 배지 없이 금액만 보여주고(예: "포장비 5,000원"), 상세에 계산식만 보여줍니다(예: "건당 500원 × 10건"). 추정이면 "추정"(합계는 "추정 포함")과 가정한 내용을, 계산에 필요한 값이 없으면 "주문 수를 입력해 주세요"처럼 넣을 값을 보여줍니다. 매출 기록 상태는 필수 비용이 모두 채워지면 '실제 비용 확인 완료' / '비용 입력 완료' / '추정 포함' 중 하나입니다. 홈의 '추정값 확인하기'에는 추정값만 나옵니다(설정대로 계산한 수수료는 제외, 정산 금액은 기록 상세에서 언제든 넣을 수 있음).
- 저장된 계산값은 설정을 바꿔도 다시 계산하지 않습니다. 기록의 금액·주문 수 등을 고칠 때만 지금 설정으로 다시 계산하며, 기록에서 직접 고른 원가율은 같은 원가율로 다시 계산합니다.
- 매출이 비어 있는 날·기록은 평균 매출 등으로 채우지 않고 '미입력'으로 둡니다.
- 분모가 0이면 "계산 불가", 데이터가 없으면 "데이터 필요"로 표시합니다(Infinity·NaN·잘못된 0% 없음).

### 비교

- 절대 증감과 증감률을 함께 표시합니다.
- 이전 값이 0이면 증감률을 생략하고 절대 변화만 표시합니다.
- 이전 영업이익이 음수이거나 부호가 바뀌면 증감률 대신 금액 변화와 흑자 전환·적자 전환·적자 축소/확대를 표시합니다.
- 비율 지표(영업이익률 등)는 %p 차이로 표시합니다.

### 문제 진단 (규칙 기반)

1. 채널별 매출 증감액을 부호와 함께 표시합니다. 증가·감소 채널이 섞여 상쇄되면 기여율을 표시하지 않습니다.
2. 수량 Q(홀 방문 고객 수, 배달·포장 주문 수)와 평균 금액 P로 분해합니다.
   수량 효과 = (Q1 − Q0) × P0, 평균 금액 효과 = Q1 × (P1 − P0). 두 효과의 합은 실제 매출 차이와 같습니다. 어느 기간의 수량이 0이거나 없으면 분해하지 않습니다.
3. 비용 항목별 총액·단위당 비용(채널은 주문당, 공통은 영업일당)·매출 대비 비율을 비교합니다. 주문이 늘어 총액만 늘고 단위 비용이 유지되면 문제로 분류하지 않습니다.
4. ±5% 이상 변화 등 정해진 규칙에 따라 **관찰 사실**, **확인할 가설**, **추가 데이터**를 나눠 보여줍니다. 원인을 단정하지 않습니다. 외부 AI는 쓰지 않습니다.
5. '먼저 확인할 문제' 순위는 **영업이익 영향** 기준입니다. 수량 변화(홀 고객 수·주문 수)는 (Q1 − Q0) × 비교 기간 단위당 남는 금액(판매 방식 비용 차감 후, 공통 운영비 차감 전)으로 계산합니다. 이익으로 바꿀 수 없는 평균 금액 하락은 "매출 영향"으로 따로 표시하고 이익 항목 뒤에 둡니다.

### 쿠폰·할인

- 가게 부담 할인액(원)은 할인·환불 상세를 입력한 기록만 더합니다. 상세 없이 순매출만 넣은 기록이 있으면 "N건 중 M건 기준"을 붙입니다.
- 할인 1,000원당 효과 = 주문 수 변화 ÷ (할인액 변화 ÷ 1,000), 남은 금액(판매 방식 비용을 뺀 금액) 변화 ÷ (할인액 변화 ÷ 1,000). 단순 전후 비교이며, 할인 상세·주문 수가 빠진 기록이 있거나 할인액 차이가 1만 원 미만이면 계산하지 않고 이유를 보여줍니다.

### 고객 지표 (선택)

- 고객 정보 없이 재주문율을 추정하지 않습니다. 기간별 집계값만 직접 입력합니다.
- 30일 재구매율 = 30일 이내 재구매 고객 수 ÷ 첫 구매 후 30일 관찰이 완료된 고객 수
- 관찰 기준일이 첫 구매 집단 종료일 + 30일 이전이면 "잠정"으로 표시합니다.
- 신규·기존은 집계 시작 전 구매 이력으로 구분하며, 기존 고객 수는 그 기간에 실제 구매한 기존 고객 수입니다. 매출 합계에 더하거나 주문 수에 곱하지 않습니다.

### 해결안

- 예상 영업이익 변화 = 예상 매출 변화 − 예상 비용 변화 (비용 증가 +, 감소 −)
- "예산을 비용 변화에 포함함"을 끄면 예산을 비용에 한 번만 더합니다.
- 템플릿 7종은 작성을 돕는 예시이며 검증된 처방이 아닙니다.

### 성과 확인

실행 전후 기간을 지정해 대상 채널과 가게 전체를 비교합니다. 단순 전후 차이를 해결안의 인과 효과로 단정하지 않으며, 다른 채널 매출이 줄었거나 전체 영업이익이 줄면 경고합니다.

- 실행 전후 영업일 수를 함께 표시하고, 다르면 영업일당 영업이익·매출을 나란히 보여주며 예상 대비 문구를 단정하지 않습니다.
- 대상 외 판매 방식의 '판매 방식 비용을 뺀 금액' 변화가 대상보다 크면 실행의 효과로 보기 어렵다고 안내합니다.
- 안내 문구는 계획의 상태값을 따릅니다(상태가 '계획'이면 날짜상 실행 기간이어도 '시작 전').
- 배달 대상 계획은 ① 배달 1건당 남는 금액 ② 배달에서 판매 방식 비용을 뺀 금액 ③ 가게 전체 영업이익을 기본 지표로 제안합니다.

## 데이터 저장 방식

- 모든 데이터는 외부 전송 없이 **현재 브라우저의 localStorage**(`restaurant-profit-beta` 키)에 저장됩니다.
- 저장 데이터에는 스키마 버전(`schemaVersion: 7`)이 붙습니다.
  - v7: 가게 설정의 식재료비 원가율 `foodCostRates`(판매 방식·원가율·적용 시작일)와 비용 값의 선택 필드 `calc`(자동 계산 내용)를 추가했습니다. 기존 데이터에는 빈 목록만 채우고 매출 기록의 비용 값(금액·근거 문구)은 바꾸지 않습니다. 변환 전 원본은 `restaurant-profit-beta:before-v7`에 한 번 보관합니다.
  - v6: 실행 계획에 함께 볼 성과지표 `extraKpis`, 쿠폰·할인 조건 `coupon`(쿠폰 금액·최소 주문금액), 결과 판단의 다음 기간 쿠폰 금액 `review.nextCouponAmount`를 추가했습니다. 기존 데이터는 빈 값으로 채우며 주 성과지표·목표·판정과 매출·비용 계산은 바뀌지 않습니다. 변환 전 원본은 `restaurant-profit-beta:before-v6`에 한 번 보관합니다.
  - v5: 매출 기록에 카드 결제액 `cardSales`를 추가했습니다(모름 = null).
  - v4: 주문 1건당 기본 비용 `perOrderCosts`를 추가했습니다. 기존 데이터는 빈 목록으로 채우며 계산 결과는 바뀌지 않습니다. 빠른 입력 때 주문 수 × 금액을 추정값으로 기록에 저장합니다.
  - 빠른 입력의 수수료 추정은 모르는 할인·환불을 0원으로 가정할 수 있으며, 그 경우 근거 문구에 가정을 남깁니다. 상세 입력의 수수료 추정은 가정하지 않습니다.
  - 홈의 영업이익은 비용이 덜 채워져도 입력된 비용만 반영한 숫자를 보여줍니다. 이때 '미확정'과 미입력 비용 개수를 함께 표시하며, 계산 규칙 자체는 바뀌지 않습니다. 이전 버전 데이터·백업은 불러올 때 자동 변환합니다.
  - v2: 해결안 목표 기준 `kpiTargetMode` 추가. 기존 데이터는 "실행 후 총량" 기준으로 채웁니다.
  - v3: 매출 금액 기준 `amountMode`(`gross` = 할인·환불 전 판매액, `net` = 순매출 직접 입력)와 `netInput`을 추가했습니다. 기존 기록은 모두 `gross`라 계산 결과가 같습니다. 이 밖에 매출 없음 확인 기록 `salesChecks`, 사용자 설정 `prefs`, 고객 지표의 출처·플랫폼 재주문율 칸, 목표 기준 증가율·영업일당을 추가했습니다.
  - 이전 버전 데이터를 변환할 때는 원본을 `restaurant-profit-beta:before-v3` 키에 한 번 보관합니다.
  - 불러오기나 변환에 실패하면 원본을 지우지 않고 `restaurant-profit-beta:recovery`에 보관하며, 첫 화면에서 파일로 저장할 수 있습니다.
- 순매출 기준 기록의 할인·환불은 상세 정보일 뿐 다시 빼지 않습니다. 판매액은 할인·환불을 모두 알 때만 복원하고, 판매액 기준 수수료 추정이나 할인 비율처럼 상세가 필요한 계산은 "추가 정보 필요"로 표시합니다.
- 기록이 없는 날·경로는 "미입력"으로 둡니다. 사용자가 "매출 없음"을 확인한 경우에만 그렇게 표시하며, 이 확인은 매출 계산에 영향을 주지 않습니다.
- 모든 화면의 기본 기간은 같은 기준일(가장 최근 매출 입력일)로 끝나는 기간입니다 (`src/domain/periods.ts`).
- 브라우저 데이터 삭제, 시크릿 창, 다른 브라우저·기기에서는 데이터가 보이지 않거나 사라질 수 있습니다. **가게 설정 → 데이터 관리**에서 JSON으로 내보내 백업하세요.
- 가져오기 전에 형식(앱 식별자, 스키마 버전, 필수 목록, 날짜·숫자 형식)을 검증하고, 덮어쓰기 전에 내용 요약과 함께 확인을 받습니다.
- 개인정보를 입력할 필요가 없도록 설계했습니다(담당자는 역할명으로 적어도 됩니다).

## 베타 한계

- POS·배달 플랫폼 연동, 결제, 메뉴판 사진 인식, 로그인·다중 사용자, 외부 AI 진단은 포함하지 않습니다.
- 매출은 일별·채널별·주문 경로별 **집계 입력**입니다. 주문 단위·메뉴별 판매량은 받지 않으므로 메뉴 원가율은 전체 원가율과 같지 않습니다.
- 정확한 레시피·재고 관리는 없습니다.
- 세무 신고용 계산이 아닙니다. 부가세는 모든 입력을 같은 기준(포함 또는 별도)으로 맞춰 입력해야 하며, 앱이 자동으로 변환하지 않습니다.
- 진단 규칙의 기준값(±5%, 비율 1%p 등)은 고정값이며 가게별로 조정할 수 없습니다.
- 데이터는 한 브라우저에만 있으므로 기기 간 동기화가 되지 않습니다.
- 대용량 데이터(수년치 일별 입력)에서의 성능은 검증하지 않았습니다.
